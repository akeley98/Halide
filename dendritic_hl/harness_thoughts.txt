Bipartite graph of Idea Nodes and Schedule Nodes

Root node is a schedule

- long term memory device for LLM autoscheduling
- benchmark hygiene: always make sure profiling results get attached IMMEDIATELY to C++ source
- basis for building future UI for humans (or planner agent) to oversee scheduling process
- for now, assume single C++ file holds everything, with conventional Halide parameterized Generator
- maximize compatibility with git or source control.
  "transparent"-ish on-disk state for catalog, designed to minimize merge conflicts.

Idea Node State:
    * ID: (parent schedule ID / proposal name)
        - short ID: proposal name prefix.{timestamp index, reverse order}
    * Parent schedule node [implied by ID]
        - parent schedule must be major
    * Proposal name [implied by ID], at most 72 characters
    * Proposal text
        - merge conflict risk, no tool is provided to fix
    * Child schedule nodes, referenced by schedule ID
        - each is just an empty file in edges/ directory with the schedule ID as name
        - needs to be consistent with schedule node state
    * Canonical schedule hash (optional)
        - merge conflict risk, fix with tool
        - canonical schedule must actually compile
    * Future work: did the idea change the algorithm?

MERGE TOOL: if there's a conflict on canonical schedule hash,
then the older schedule is chosen as the true canonical schedule.
Then a child idea node (proposal name: merge_conflict_<timestamp>)
is added with the newer schedule as its canonical schedule.
This order is needed for the DAG invariant.

Schedule Node State:
    * ID: timestamp + schedule hash
        - short ID: proposal name prefix.{timestamp index, reverse order} [canonical schedule of idea node]
        - short ID: proposal name prefix.{timestamp index, reverse order}.{timestamp index, forward order} [any schedule]
        - short ID: shortest unique hash prefix
        - short ID: hash prefix:{timestamp index, reverse order} [eh who cares]
    * Wall clock timestamp [implied by ID]
    * Parent idea node(s)
        - list of files on disk (rare case: multiple parents due to git merge behavior)
        - 0 parents for "fresh start"
        - Parent's parent schedule must have timestamp before this schedule's timestamp (enforces DAG)
        - 0 parents or is canonical schedule of any parent means this schedule is major
        - otherwise this schedule is minor
    * C++ schedule
        - strip RHS from "DENDRITIC_HL_IDEA=RHS" comment from schedule before storing+hashing; restore when loading
            - multiple parents leads to error; asked to clarify which one by providing short ID with parent name
    * Compilation result (C++ compile fail, Halide compile fail, success)
    * Set of benchmark or profiler results in JSON.
      Each file name is timestamped with microsecond precision.
      Annotated with some system information + generator parameter values.
        - tiny merge conflict risk.
    * Advised generator values as JSON with comment
    * Commentary files (commentary + timestamp + importance)
        - should explain what went wrong for non-canonical schedule
        - should be post-mortem of performance/effect for canonical schedule
        - importance propagates to parent idea node importance, if canonical
        - merge conflict risk for timestamp collision; no tool to fix

TOOL: can parent a schedule node after-the-fact to another schedule node, with an intervening parent idea node.

Node State:
    * Directory named by
        * If root: roots/random-hash.proposal-name
        * If child: parent-hash.children/proposal-name
      proposal name is up to 80 characters with only alnum and underscore
      random-hash is totally random.
      parent-hash is that of the parent node for child.
    * All other state is in the directory.
    * Hash of this node (node-hash) is hash of (proposal name, random-hash or parent-hash).
    * Proposal text.
    * Implied state: child nodes, they are directories matching *.node-hash.child
      ONLY NODES WITH canonical schedules can have child nodes, if state is consistent.
    * MERGE RISK: Hash of parent node's canonical schedule (if this is not a root node)
    * Set of C++ files, each ID'd by their hash; plus with sub-directory containing
        * Compilation result (C++ compile fail, Halide compile fail, success)
        * Set of benchmark results in JSON. Annotated with some system information.
        * MERGE RISK: Commentary on why the schedule was discarded, if not canonical.
    * MERGE RISK: Optional canonical schedule hash.
    * Optional post-mortem notes, only with canonical schedule and annotated with canonical schedule hash.
