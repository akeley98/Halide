# How to read this file

These are COVERAGE MILESTONES, not a doc outline and not an ordered to-do list.
Each milestone names a cluster of Halide features that `loopdoc.md` should explain
*correctly and holistically* -- i.e. the doc reads as a coherent whole, and a
micro-agent can reconstruct the loop nest for examples exercising those features
without reading the source.

Because every feature interacts with every other, ordering is a rough guide only.
Skip ahead or double back as judgment dictates.

Marking convention:
  [ ]    not started
  [WIP]  in progress (only one at a time, normally)
  [✅]   the doc explains this well enough that micro-tests covering it pass

"Done" is a judgment call, especially for early milestones -- revisit freely.

[✅] `split`, `fuse`, `tile`, `reorder`
    NOTES:
      * DONE (delegated). Main agent wrote loopdoc §6 (new) + a §5 rewrite that
        introduces the mutable, innermost-first **dimension list**; src_doc §10;
        and examples. A logged micro-agent implemented all four transforms in
        micro_halide from the docs ALONE -- all examples passed on the first run,
        integrity clean (no Halide-source/src_doc reads, read loopdoc.md, no
        commits), and it reported NO doc gaps. Strong signal §5/§6 are clear.
      * MODEL: each transform rewrites the dim list (which drives both loop
        emission and the set of legal compute_at/store_at site names):
          - split(old,outer,inner,f): replace old with [inner,outer], inner
            innermost -> +1 loop; inner gets a constant bound (normalized away).
          - fuse(inner,outer,fused): remove both, put fused at inner's slot -> -1.
          - reorder(v_in..v_out): permute ONLY the named dims among the slots
            they currently occupy; unnamed dims stay put. PARTIAL reorder (fewer
            vars than dims) is a real, separately-tested code path.
          - tile(x,y,xo,yo,xi,yi,xf,yf) = split(x..)+split(y..)+
            reorder(xi,yi,xo,yo) -> +2 loops, list [xi,yi,xo,yo] innermost-first.
      * VISIBILITY (confirmed): a pure-serial reorder, and the inner/outer order
        of a split, are INVISIBLE to print_loop_nest -- tested only via a
        TOPOLOGICAL CONSEQUENCE (reorder relocates a compute_at producer to a
        different host loop: reorder_topological vs reorder_baseline). Will become
        directly visible once loops carry distinct types (vectorize/parallel/
        unroll), which the canonicalizer DOES keep -- a later milestone.
      * Examples: split_basic, fuse_basic, tile_basic, reorder_baseline,
        reorder_topological, split_compute_at; negatives neg_reorder_bad_var and
        neg_compute_at_fused_away (compute_at at a fuse-consumed var -> only the
        fused var is a legal site). Adversarial follow-ups (main agent, all pass,
        confirm no overfit): reorder_partial, fuse_compute_at (positive: fused
        var IS a legal site), split_twice (split a split-produced var). 42 total.
      * Loop elision is handled by the `micro_halide_collapses` annotation (see bootstrap),
        so this milestone does NOT need to make bounds inference predictable.
        Keep declaring elision via `micro_halide_collapses`; do not try to derive it.
      * split/fuse/reorder DO add/rename/merge loops the schedule controls
        directly -- those are structural and must be derived (not declared).
        Watch the interaction: a split introduces new Vars that can themselves
        be compute_at sites and can be elided; `micro_halide_collapses` keys on Var name,
        so annotate the post-split Var names.
      * GOTCHA (from canonicalize.py, important for designing reorder tests):
        the canonicalizer DROPS loop variable names and keeps only loop TYPE
        (for/parallel/...) + nesting. So a pure serial `reorder` of two plain
        `for` loops is INVISIBLE to the comparison (both sides print just
        `for`/`for`) -- a reorder-only example would pass trivially and prove
        nothing. To actually test reorder, give it a *topological consequence*:
        e.g. reorder so a compute_at producer ends up under a different loop, or
        combine with a loop-type change (vectorize/parallel/unroll, a later
        milestone) that the canonicalizer DOES keep. Same caveat for the order
        of split's inner/outer loops when both are plain serial.
      * split's inner loop is named like the split var; bounds become constant
        (split factor) for the inner loop -- but canonicalize normalizes constant
        bounds away, so only the *number* and nesting of loops is the signal.
        micro_halide will need real Var objects for the new split/fuse vars
        (Var x_outer, x_inner; f.split(x, x_outer, x_inner, factor)) so that
        compute_at/store_at can later name them.

[WIP] Update definitions (see e.g. `../apps/hist`)
    NOTES:
      * MODEL (explored, verified against Halide):
        - A Func has an ordered list of STAGES: stage 0 = pure/initial def, then
          one stage per update definition (definition order). All stages are
          emitted inside ONE `produce f` block as consecutive SIBLING loop nests
          (NOT separate produce/consume per stage). A consumer's `consume f`
          wraps the whole produce (it reads the final, post-update value).
        - Stage 0's loops = the Func's pure dimension list (as before, §5/§6).
        - An update stage's loops = its OWN dimension list = the free Vars on its
          LHS + the RVars of any RDom it uses. Default order (innermost-first):
          RVars innermost, and WITHIN the RVars the first-declared (r.x) is the
          INNERMOST (Var convention: first dim fastest -- CORRECTED; an earlier
          note said r.x outer, which was wrong and hidden by name-dropping until
          producer_at_2d_rvar pinned it down). Pure free vars sit outside the
          RVars (first LHS arg innermost among the pures, per §5). A pure
          dimension whose LHS slot holds an RVar/expr (e.g. f(x,r)=... or the
          scatter hist(in(r))) does NOT loop in that stage.
        - RVars print as `for r in [min,max]` -> canonicalize drops the bound, so
          just another `for`. A k-dimensional RDom adds k nested reduction loops.
        - Each stage is scheduled INDEPENDENTLY: `f` schedules stage 0; `f.update(i)`
          returns a Stage handle for update i. split/fuse/reorder/tile (and later
          loop types) apply PER STAGE, on that stage's dim list (which can include
          RVars). E.g. f.update(0).split(x,..) leaves the init stage untouched.
        - compute_at/store_at are per-FUNC: the whole `produce f` (all stages)
          moves to the site. An RVar loop of ANY stage is a valid compute_at site
          for a producer; the producer is injected into that stage's loop.
        - LEGALITY: the §8 legal-site rule now intersects uses across ALL stages.
          A producer computed at an RVar loop (which exists only in its own stage)
          is illegal if the producer is also used in another stage; legal sites
          are the loops common to every stage's use (+ root). Verified:
          neg compute_at(f, r) when p is used in both s0 and s1.
      * OUT OF SCOPE (like bounds inference): reordering RVars in a
        non-associative/non-commutative reduction is illegal, but detecting this
        needs SEMANTIC analysis of the update arithmetic, which micro_halide's
        Expr deliberately discards (it tracks only deps). Document the rule
        qualitatively; do NOT make it a micro_halide-checked test.
      * SCAFFOLDING SPLIT: main agent imitates the API (RDom/RVar/Stage,
        operator+=/*=, second operator= => update stage, Func::update(i)) and
        captures each stage's raw data; micro-agent implements the loop-nest
        EMISSION for stages from the docs. apps/hist uses .update().reorder(...)
        and .rfactor(...) in the wild -- good citation.
