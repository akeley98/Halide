# How to read this file

These are COVERAGE MILESTONES, not a doc outline and not an ordered to-do list.
Each milestone names a cluster of Halide features that `loopdoc.md` should explain
*correctly and holistically* -- i.e. the doc reads as a coherent whole, and a
micro-agent can reconstruct the loop nest for examples exercising those features
without reading the source.

Because every feature interacts with every other, ordering is a rough guide only.
Skip ahead or double back as judgment dictates.

Marking convention:
  [ ]    not started
  [WIP]  in progress (only one at a time, normally)
  [✅]   the doc explains this well enough that micro-tests covering it pass

"Done" is a judgment call, especially for early milestones -- revisit freely.

[✅] `specialize`
    NOTES: may run into test harness bugs here with loop nest diffing.
    Micro-agent should stop and report problems back to the main agent
    if this is the case.

    User request: consider a function f that is specialized and consumes function g.
    Similar to clone, the specialized f doesn't transitively specialize g.
    (Correct me if I'm mistaken).
    This leads to three cases to carefully probe.
    First, having g be compute_at/store_at/hoist'd differently depending on which specialized f is the caller (easy case).
    Second, having g be scheduled differently internally depending on which specialized f is the caller (hard case, requires g clone/wrapper?)
    Third, the previous case except we care about specializing some h that g consumes based on which specialized f is the ultimate caller (even harder case, chain of g/h clone/wrapper?)

    Don't trigger the Halide behavior where `specialize(...)` with an already-seen Expr returns an existing specialization,
    and not a new specialization.

    --- main-agent findings (probe/SPECIALIZE_FINDINGS.md + probe_specialize*.cpp) ---
    * MODEL: each Definition (pure + each update) carries an ordered
      specializations list; specialize() forks a COPY of the schedule-so-far and
      returns a handle to it (later directives on the handle -> branch;
      directives on the Func after specialize() -> fallback). specialize_fail
      terminates the chain. Lowering (ScheduleFunctions.cpp ~518-544): nested
      IfThenElse, folded last-to-first, so `if c0{s0} else if c1{s1}...
      else{fallback}` in declaration order, fallback last; specialize_fail's else
      is an assert (no loops).
    * RENDERING: PrintLoopNest has NO IfThenElse visitor -> both branches print
      CONCATENATED as sibling subtrees under ONE `produce`, no if/else text, no
      condition. Two simplifier effects: (a) specialize_fail prints no fallback;
      (b) IDENTICAL-branch merge (simplify folds if/else with byte-identical IR
      into one) -- a no-op specialization vanishes. A branch differing only in a
      canonicalize-invisible way (serial-loop order, const bounds) is still a
      distinct IR nest and prints separately.
    * HARNESS: the concatenated multi-branch output PARSES cleanly in
      canonicalize.py (sibling subtrees under produce F0); the anticipated
      "loop-nest diffing bug" did NOT materialize for distinct-branch examples.
      The real subtlety is the identical-branch MERGE: micro must emit one copy
      per branch and merge two adjacent copies only on TRUE IR identity, not
      canonical identity (else it would wrongly merge a reorder-only branch).
      All committed examples have STRUCTURALLY DISTINCT branches, so no merge is
      exercised -- micro can emit one-nest-per-branch without merge logic for now.
    * THE THREE USER CASES: the human is CORRECT that specialize does NOT
      transitively specialize a callee. specialize forks ONLY the specialized
      Func's own schedule; a callee has ONE definition + ONE schedule shared by
      all branches. So:
        - Case 1 (producer placed differently per branch): achievable -- the only
          per-branch variation is PLACEMENT, when the compute_at level names a
          loop the branch moved (per-branch reorder/split/rename). Documented
          (loopdoc §15). BUT a producer at a *different loop* per branch gets
          different bounds -> different elided loops per branch, which the
          per-producer-stage micro_halide_collapses API cannot express (see the
          [open] gap below). specialize_producer_at.cpp uses the SYMMETRIC-elision
          variant (producer at the same var in both branches, f's outer loop
          split) to stay testable.
        - Cases 2 & 3 (callee scheduled differently INTERNALLY per branch): NO
          SCHEDULE-ONLY mechanism (the user's assessment, confirmed). specialize
          forks only the consumer's own schedule; clone_in/in give ONE shared
          wrapper/clone schedule read in all branches (probe_specialize_case2.cpp
          (1)/(2): the clone is tiled IDENTICALLY in both branches). The ONLY way
          to get per-branch producers is an ALGORITHM select: f = select(cond, g,
          gc) + f.specialize(cond), where simplify_specializations prunes the
          select per branch so each injects only its named producer, independently
          scheduled (probe (3): tiled g in one branch, plain gc in the other). But
          that CHANGES what f computes and has NO equivalence safety net (Halide
          never checks g==gc), so it sits OUTSIDE the algorithm/schedule
          separation -- a workaround, not a scheduling answer. Case 3 = same one
          level deeper (duplicate the g/h sub-chain). Dead-branch elimination is
          EARLY (simplify_specializations, before schedule_functions), so a
          producer dead in a branch imposes NO scheduling constraint there
          (probe_specialize_deadbranch.cpp (b) legal; (c) errors only from the
          LIVE branch). loopdoc §15 "Producers under a specialized consumer"
          rewritten to this (was overclaimed as "not expressible"). Probes +
          SPECIALIZE_FINDINGS.md "Case 2/3" section seed the design discussion.
          No harness example (select needs Expr analysis micro_halide lacks).
    * CONDITION DE-DUP: OUT OF SCOPE per the human note above -- every example
      uses DISTINCT conditions (separate Param<bool>s), so micro need not cache

    * MICRO SCAFFOLD (this commit): added Param<T> (converts to Expr) + THROWING

    * EXAMPLES (16 positive + 1 negative; rfactor_specialize listed under the
