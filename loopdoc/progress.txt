# How to read this file

These are COVERAGE MILESTONES, not a doc outline and not an ordered to-do list.
Each milestone names a cluster of Halide features that `loopdoc.md` should explain
*correctly and holistically* -- i.e. the doc reads as a coherent whole, and a
micro-agent can reconstruct the loop nest for examples exercising those features
without reading the source.

Because every feature interacts with every other, ordering is a rough guide only.
Skip ahead or double back as judgment dictates.

Marking convention:
  [ ]    not started
  [WIP]  in progress (only one at a time, normally)
  [✅]   the doc explains this well enough that micro-tests covering it pass

"Done" is a judgment call, especially for early milestones -- revisit freely.

        the nesting depth follows each producer's compute level, not the
        dependency graph. Same level -> nested chain in tie-break order; different
        levels -> outer-level producer wraps inner-level producer; root+at mixes

      * NEGATIVE EXAMPLES (illegal compute_at; both Halide and micro_halide must

        loop stacks across all uses, + root; ComputeLegalSchedules). Three
        structural failures, none bounds-dependent:
          - neg_compute_at_bad_var.cpp: loop var not a dim of the host.
          - neg_compute_at_nonconsumer.cpp: host (realized) does not read f.
          - neg_compute_at_two_consumers.cpp: f used at two root sites, computed
            inside one -> only root is legal. (THE producer/consumer break.)
        micro_halide validates this in LoopNestPrinter::validate (host realized,
        loop exists, every reader enclosed_by the site). loopdoc §7 "When a
        compute_at is illegal" + src_doc §6 document/justify it.
      * compute_at loop ELISION resolved via the design decision below: the loop
        *structure* is derived from the schedule (validated), and point-loop
        elision (extent-1 dims simplified away) is *declared* per example with

        (compute_at_elided_level.cpp). README documents the structure-vs-declared
        factoring. This is the standing policy for all future bounds-driven
        elision (incl. RDom/update reduction loops).

[ ] `in` (wrapper functions) and `clone_in`
    NOTES:
      * Realization-order tie-break (see bootstrap): sibling producers are
        ordered by (name prefix, first-visitation order, full name). Wrappers
        and clones are auto-named from the wrapped Func (e.g. `f`, `f_in_g`,
        clones sharing a prefix), so several siblings can share a name PREFIX.

        Halide's populate_environment_helper walks IR calls.

        and trailing digits actually show up.

        this milestone lands, add the positive version -- give one consumer its
        own `f.in(consumer)` so each wrapper has a single consumer and can be
        compute_at'd legally. Cross-check it against that negative example so the
        before/after contrast is documented.
